SLIDE 02

JWT를 선택한 것이 아니라,
JWT의 한계를 통제하기로 결정했다

SECURITY DECISION

Stateless 인증의 확장성을 유지하면서 Token Revocation과 Replay 대응까지 확보한다.

01 / RISK

우리가 통제해야 할 위협

HIGH RISK
01
Access Token 탈취 서명 검증만으로는 탈취된 토큰을 즉시 폐기할 수 없음
02
Logout 이후 Token 재사용 Stateless 특성상 서버가 토큰 상태를 알 수 없음
03
Refresh Token Replay 동일 Refresh Token의 반복 사용 가능성을 차단해야 함
04
Session Store 확장성 부담 서버 세션 의존도를 높이면 Scale-out 비용이 증가
02 / CONTROL

위협을 통제하는 설계

CONTROLLED
ACCESS TOKEN JWT
Stateless 서명 검증으로 요청 인증
REFRESH TOKEN HttpOnly Cookie
JavaScript 접근을 차단하고 브라우저 쿠키로 전달
TOKEN ROTATION RTR + JTI
Refresh Token 사용 시 새로운 Token으로 교체
REVOCATION Redis
Logout · 재사용 감지 시 폐기 상태 반영
03 / RESULT

결과적으로 확보되는 보안 속성

VERIFIED
✓
Fast Verification Access Token은 서명 검증 중심으로 처리
✓
One-time Refresh RTR로 Refresh Token 재사용 검출 및 거부
✓
Immediate Revocation Redis 기반으로 폐기 상태를 즉시 반영
✓
Horizontal Scaling 애플리케이션 서버 간 세션 공유 불필요
CORE PRINCIPLE Stateless 인증 + Stateful 제어 JWT는 빠르게 검증하고,
폐기가 필요한 상태만 Redis에서 관리한다.
